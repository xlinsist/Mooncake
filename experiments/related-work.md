# Related Work

Prior work expanded KV cache capacity through memory virtualization,
multi-tier offloading, disaggregated cache pools, and I/O-aware restoration.
These directions established the value of moving KV cache beyond GPU memory,
but they addressed different layers of the serving stack. We group them by the
system boundary they optimize and distinguish their goals from transparent
object storage across local NVMe and NVMe over Fabrics (NVMe-oF).

## KV Cache Memory Management and Offloading

Early LLM serving systems primarily treated KV cache management as a memory
capacity and allocation problem. PagedAttention introduced block-based KV cache
management to reduce fragmentation and enable sharing between requests [1].
FlexGen extended the memory hierarchy across GPU memory, host memory, and local
storage, and used an offline placement plan to improve throughput on a
memory-constrained GPU [2]. InfiniGen reduced host-to-GPU traffic by predicting
and fetching only the KV entries needed by subsequent attention operations [3].
These systems established that logical KV blocks can be separated from their
physical location and that slower storage can expand effective capacity.
However, their placement decisions remained part of a serving engine or an
offloading plan. They did not define a backend-independent object interface
that transparently selects between local NVMe and NVMe-oF while preserving the
same object semantics.

## Multi-tier and Disaggregated KV Cache Systems

Recent systems moved KV cache beyond a single inference process and managed it
as shared state. Mooncake introduced a KV-cache-centric disaggregated serving
architecture and a distributed cache pool spanning otherwise idle memory and
storage resources [4]. Its Store exposed object operations and replica
metadata, but callers still participated in replica and segment selection. The
present work extends this storage boundary by moving local NVMe and NVMe-oF
selection into the Store and making the selected backend a deployment concern.

LMCache provided a pluggable KV cache layer across inference engines and
multiple storage or transport connectors [5]. CachedAttention coordinated
cache fetch and eviction across GPU memory, host memory, and storage according
to scheduler hints [6]. MemServe organized distributed CPU and GPU memory as an
elastic pool and managed context-cache insertion, lookup, transfer, and
reclamation [7]. These systems demonstrated the value of stable cache APIs,
multi-tier capacity, and topology-aware movement. Their primary abstractions,
however, focused on cache policy, connectors, or distributed memory resources.
They did not make a committed object remain backend-independent across
allocation, publication, deletion, and client restart for both local NVMe and
NVMe-oF.

## KV Cache Transfer and I/O Coordination

Another line of work reduced the cost of moving or reconstructing KV cache.
CacheGen compressed and streamed KV tensors to reduce network transfer delay
[8]. CacheBlend combined selective recomputation with cache loading so that
reused knowledge could reside on slower storage [9]. Cake scheduled KV loading
and recomputation together and selected between them at chunk granularity [10].
CachedAttention similarly overlapped storage operations with inference, while
HCache used chunked storage and restoration to reduce recovery stalls [6, 11].
An empirical NVMe study further characterized the block I/O generated by model
and KV cache offloading and showed why request size and read/write asymmetry
must be considered when evaluating a storage path [12].

These techniques are complementary to backend transparency. Compression,
prefetching, recomputation, and compute-I/O overlap can reduce the visible cost
of a chosen backend, but they assume that the system has already located a
valid cache object. Our work instead defines how the Store chooses the backend,
records its location, routes later operations, and prevents incomplete writes
from becoming visible. It therefore provides a storage contract on top of
which these transfer optimizations can operate.

## Stateful Serving and Recovery

Stateful serving systems considered how model or request state survives
eviction, migration, and process changes. Pensieve retained multi-turn state
across GPU and CPU memory and selectively restored or recomputed evicted
tokens [13]. HCache persisted intermediate state on NVMe and coordinated
loading with recomputation to accelerate restoration [11]. ServerlessLLM used
multi-tier checkpoint loading and locality-aware instance placement to reduce
model startup and migration delay [14]. MemServe also reclaimed memory after
detecting failed instances [7]. These systems showed that storage placement
and recovery must be coordinated with runtime state.

Their recovery units and guarantees differ from those required by a KV object
store. A restored model checkpoint, a recomputed token range, or a reclaimed
memory allocation does not by itself specify when a newly written object
becomes visible, how a failed write is revoked, or how a restarted client
reconstructs the route to an already committed replica. Our design binds
placement metadata to a prepare, write, commit or revoke, read, and remove
lifecycle. The resulting guarantee is deliberately narrower than
high-availability recovery: while the metadata service remains available, a
client can rediscover committed local NVMe or NVMe-oF objects after restart,
and an unsuccessful write is not published as a readable object.

## Positioning Summary

Table 1 summarizes the distinction between representative systems and this
work. The comparison does not claim that all prior systems should provide the
same semantics. Instead, it identifies the unaddressed system boundary studied
here: backend selection and lifecycle management inside a unified object
Store. This work does not propose a dynamic optimal placement policy. It
provides configuration-driven placement, metadata-based routing, and a common
lifecycle so that deployment policy can change without changing the upper-level
`put`, `get`, and `remove` logic.

| System | Local and remote storage | Backend hidden from caller | Committed placement metadata | Failed-write revocation | Client-restart route recovery |
|---|:---:|:---:|:---:|:---:|:---:|
| Mooncake [4] | Partial | Partial | Yes | Not a cross-backend contract | Not explicitly defined |
| LMCache [5] | Yes | Partial | Connector-specific | Not a primary guarantee | Not explicitly defined |
| CachedAttention [6] | Yes | No | Cache state | No | No |
| MemServe [7] | Distributed memory | Yes | Instance and index state | Failure reclamation only | Limited |
| HCache [11] | SSD with memory fallback | No | Restoration metadata | Not a primary guarantee | Not explicitly defined |
| This work | **Local NVMe and NVMe-oF** | **Yes** | **Yes** | **Yes** | **Yes, with metadata service available** |
