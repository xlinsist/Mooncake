**核心判断：** CetoFS 的主要洞察是：远程 SSD 的性能问题不仅在传输协议，也在文件系统把哪些事情留在主机上执行。把长时并发等待和日志 checkpoint 留在主机，会把网络往返带进串行路径；把数据路径移到用户态，又必须重新解决块访问权限。论文用可信存储端统一承接这三类工作，并保留内核文件系统管理元数据。其性能证据在单 initiator、单 target、单 Optane SSD 上较完整；多主机一致性、故障恢复验证和资源成本证据则不足。

## 1. 标题深度分析

**CETOFS: A High-Performance File System with Host-Server Collaboration for Remote Storage**

| 关键词 | 实际含义 | 不应过度解读之处 |
| --- | --- | --- |
| CetoFS | 本文文件系统原型的名称 | 原文没有解释名称词源 |
| High-Performance | 降低访问延迟，提高共享文件并发吞吐，减少原子写网络流量 | 不意味着所有工作负载都有数量级收益 |
| File System | 仍提供文件、目录、权限和文件偏移语义 | 不是仅提供远程裸块设备的 NVMe-oF 优化 |
| Host-Server Collaboration | 主机 U-Lib、主机 K-FS、存储端 T-Handler 分工 | “协同”具体指授权建立、数据访问、排序和事务管理之间的信息传递 |
| Remote Storage | 通过 RDMA 访问分离式 NVMe SSD | 已评估范围不是通用分布式文件系统，也不是无 CPU 的 NIC 全卸载模式 |

**一句话概述：** 在主机保留成熟的文件元数据管理，让用户态直接发出数据请求，并由可信存储端检查权限、执行顺序和完成日志事务，以减少远程访问中重复的软件处理与网络等待。

<a id="section-4"></a>
## 4. 摘要与关键词提炼

### 摘要完整要点重述

RDMA 网络和低延迟 NVMe SSD 使存储资源分离具有吸引力，但把现有内核文件系统直接放在远程块设备上，仍会受到软件栈、跨网络的并发串行化和事务数据搬移限制。CetoFS 保留内核控制路径，把常规数据访问放进用户态，并利用存储端 CPU 处理数据请求授权、并发请求排序和失败原子性。作者实现了相应原型，与内核及用户态文件系统比较，在所测负载中报告单线程文件访问延迟最多下降 52%、并发访问吞吐最高达到其所述 19× 改善。

**原文关键词栏：** 论文没有独立列出的 Keywords 栏。以下为报告归纳的检索词，不是作者原样给出的关键词：分离式存储、NVMe-over-RDMA、用户态文件系统、反向权限表、并发控制卸载、请求分组、redo logging、failure-atomic IO。

### TL;DR：有它和没有它差在哪里

设想多个线程访问同一个远程文件。传统路径可能要求一个写请求拿着文件锁，等远端 SSD 完成并收到回复后，下一个请求才能出发。CetoFS 让主机先用短锁确定顺序，再把多个请求同时发出去，远端根据是否冲突安排执行。与此同时，数据访问不用反复穿过内核，但远端检查请求的块确实属于已获授权的文件；原子写的日志及 checkpoint 也留在远端。它减少的是软件路径、被串行化的网络阶段和日志的跨网重复搬运，未消除真正冲突操作的顺序约束或 SSD 内部写放大。

## 6. 背景部分深度分析

### 为什么要讲 NVMe-oF 的 initiator 和 target

NVMe-oF 使远端 SSD 在主机上表现为块设备，因此 Ext4/F2FS 可以直接使用它。但“接口像本地设备”不等于“每次操作成本像本地设备”：本地一次阻塞 I/O，远程会经过请求发送、远端处理和回复阶段。这个区别支撑后文对锁和 checkpoint 位置的重设计。

**图 1（p.661）：基于 NVMe-over-RDMA 的内核文件系统路径。** 主机应用经过 syscall、文件系统、NVMe 驱动、NVMe-over-RDMA 驱动；target 解码命令后通过自己的内核路径访问 SSD。以写为例，请求通过 RDMA_SEND 发送，target 以 RDMA_READ 取数据，完成后再发送响应。读则需要把数据 RDMA_WRITE 回主机。此图的功能是列出实际付费的软件环节，说明 RDMA 并不自动绕过文件系统及协议栈。

### 为什么选择 CPU mode

作者区分 target CPU 处理命令的 CPU mode 与 NIC 直接访问 SSD 的 offload mode。本工作采用前者，既因为它便于放置权限、排序和日志处理，也因为作者引用既有研究说明特定硬件卸载路径可能性能不佳。引用中的“最多 88% 退化”不是 CetoFS 本文重新测出的结论，也不代表所有 NIC/DPU 卸载实现。

原文将传统 TCP 栈概括为毫秒级、RDMA 为微秒级。这一概括不足以推出“TCP 远程存储必然不能低延迟”；本文未直接比较优化后的 NVMe/TCP、i10 和 RDMA。因此它能支持作者选择 RDMA 的研究设置，不能替代传输方案的公平比较。

### 为什么保留内核元数据

数据路径高频，而命名空间、分配和权限管理复杂。复用 Ext4 可以减少重新实现控制语义的负担。代价是 append、频繁 open、小文件及元数据密集场景仍会进入内核；后文 Varmail 收益有限恰好验证了这条边界。

## 7. 动机分析

### 7.1 表 1：网络之外，软件成本更大

**表 1（p.661）研究问题：** 把 SSD 变成远程设备后，额外延迟主要来自哪里？单位均为 µs，操作为 4KB 随机访问。

| 路径 | 读 | 写 |
| --- | ---: | ---: |
| Dev-L：本地裸设备 | 7.01 | 7.04 |
| Dev-R：远程裸设备 | 14.38 | 14.23 |
| Kernel-L：本地文件系统 | 13.56 | 14.27 |
| Kernel-R：远程文件系统 | 42.34 | 40.91 |

远程裸设备比本地多约 7µs，但远程文件系统访问比本地多约 27–29µs。**分析：** 硬件网络增量解释不了全部退化，必须继续拆软件路径；这使“只换更快网卡”无法充分回应问题。

### 7.2 表 2：定位可以移除的开销

**表 2（p.661）研究问题：** 4KB 随机写的 40.91µs 分别花在哪里？

| 组成 | 延迟（µs） | 原文占比 |
| --- | ---: | ---: |
| Syscall | 0.61 | 1.5% |
| FS stack | 7.42 | 18.1% |
| NVMe driver | 3.90 | 9.5% |
| NVMe-over-RDMA driver | 14.75 | 36.1% |
| Device time | 7.04 | 17.2% |
| Network time | 7.19 | 17.5% |
| Total | 40.91 | 100% |

软件四项合计 26.68µs，约 65.2%；驱动中断处理是作者解释 NVMe-over-RDMA 栈成本的重点。占比逐项四舍五入后不必精确相加为 100%。这里的关键不是 syscall 的 0.61µs，而是整条远程内核处理路径。

### 7.3 图 2、图 3：网络时间为什么会变成可扩展性问题

**图 2（p.662）：并发写吞吐。** 多线程更新同一个 10GB 文件，对比 Ext4/F2FS 的本地和远程模式。原文观察到远程吞吐比本地下降 63%；线程从 1 增到 20 时，远程吞吐又下降约 30%。此图说明添加线程不能自动提高设备利用率，但它测的是共享文件负载，不能推广成所有内核文件系统并发访问都不能扩展。

**图 3（p.662）：串行化时间线。** T1 持锁期间不仅做 SSD I/O，也等待网络。T2/T3 连发出请求都要等。原文列出的额外等待为 26.6µs 和 53.2µs；应结合图中的完整远程阶段理解，不能把它当作表 2 单独的 7.19µs 物理网络时间。

**从定量到定性：** 锁覆盖远程往返后，队列长度增长会重复支付通信等待；应用看到的是延迟堆积和吞吐停滞，设备却未必忙满。这是同步位置错误导致的资源利用问题。移到用户态只能减小常数项，不能自动改变串行依赖关系，因此还需要并发控制卸载。

### 7.4 图 4：事务为什么造成重复跨网传输

**图 4（p.662）：传统 journaling 数据流。** 主机把日志写到远端，然后 checkpoint 从远端读取日志、再把数据写到远端正式位置。图示路径包含日志上行、日志下行和正式位置上行，还可能有日志元数据 I/O。

其证据支持“把 checkpoint 放到 target 能减少跨网搬移”。但主机是否仍缓存日志会影响读回成本，不能把三次完整负载跨网当成所有 journaling 实现的恒定代价。CoW 的额外索引更新也是作者动机的一部分，本文未单独测出所有 CoW 文件系统的网络放大。

## 8. 方法逐项精读

<a id="architecture"></a>
### 8.1 架构与权限检查：绕过内核后如何保住边界

**图 5（p.663）：整体架构。** 三个组件分别负责：

| 组件 | 输入与输出 | 核心责任与原因 |
| --- | --- | --- |
| U-Lib，主机用户态库 | 文件操作 → 控制操作转发或块级数据请求 | 拦截调用；缓存 offset-to-block 映射；直接通过 RDMA 发数据请求 |
| K-FS，主机内核文件系统 | open/分配等操作 → 元数据更新及授权队列 | 复用 Ext4 的命名空间、文件分配与打开时权限检查 |
| T-Handler，存储端用户态进程 | 数据请求 → 权限检查、SSD I/O、完成响应 | 在可信目标端执行主机用户态不能被信任执行的检查，并承接排序和日志 |

K-FS 与 target 通过 admin queue 通信。每个打开文件使用 `server_rb` 请求环及 `host_rb` 完成环。U-Lib 以 RDMA_WRITE_WITH_IMM 通知请求位置，target 由此定位请求而不是扫描所有文件环；U-Lib 轮询完成标记。论文说 immediate data 携带地址，但没有展开地址宽度及编码实现，复现时需要确认实际使用偏移、索引还是受限地址。

**open 建立能力。** U-Lib 建立 `host_rb`，调用新增 `ceto_open`，K-FS 检查进程权限，再要求 target 建立 `server_rb` 并交换 RDMA 访问参数。之后常规 read/write 可以绕过内核。文件队列和 RDMA QP 不同：原文按 initiator 线程分配 QP，而不是每个文件一个 QP。实现上支持最多 64K 个并发打开文件；按相同权限合并队列只是缓解上限的建议，未在实验中验证。

**偏移映射。** U-Lib 为每个文件缓存 extent tree，映射缺失时用 `fiemap ioctl` 向 K-FS 查询。设 extent 数为 E，常见平衡树实现的查找可按 O(log E) 理解，但原文未给出树实现的完整复杂度证明。论文采用 concurrent reads 或 exclusive write 的文件共享策略，以避免多个 U-Lib 的写映射同步；这不等于禁止同一 U-Lib 中的多线程写，也不能据此宣称支持任意跨进程、多主机并发写。

**反向权限表。** 常规映射回答“文件偏移在哪个块”；反向权限表回答“这个块属于哪个文件”。每块一个 8 字节 owner ID，数据块 owner 为 inode，空闲块和元数据块 owner 为 K-FS 的 0。4KB 块可存 512 项，空间比例为 8/4096 ≈ 0.1953%；作者以 1TB SSD 约需 2GB 表空间说明开销。target 用 radix tree 缓存表页，缓存单位是包含 512 项的设备块。

权限检查必须同时满足：请求操作符合该队列的读写权限；请求涉及块的 owner 与队列绑定文件一致。权限表更新由 K-FS 写入文件系统 journal 后通知 target 更新缓存。**为什么有效：** 即使 U-Lib 伪造 offset 映射或裸 LBA，也不应越过 target 的块归属检查；元数据和空闲块不会因“地址可达”就允许用户写入。

**图 6（p.664）：一次读的完整闭环。** `pread(A, ..., 0x1000)` 先被转换为 LBA `0x6000`，请求从 A 的队列到达 target；target 同时验证读权限与块 owner，合法才访问 SSD并回复。此图是图 5 的具体化，解释了用户态地址转换不是安全依据，可信端重新检查才是。

**append 边界。** 新增数据没有映射和权限项，先 `fallocate` 分配，再走用户态写入。后台预分配是可选优化思路，不能直接计入所有已测收益。作者称 append 的崩溃一致性保持 Ext4/XFS metadata-journaling/write-back 水平，不能等同于 §5 显式事务 API 的失败原子性。

**需要进一步证明的安全环节：** 关闭文件、撤销访问、truncate 后重分配、inode 重用、过期 rkey 与在途请求之间的顺序。原文提出 journal 和缓存更新，但未完整描述这些竞态；这是协议证据缺口，并非已证实存在漏洞。

<a id="concurrency"></a>
### 8.2 并发排序：把“决定顺序”和“等远端完成”分开

#### 图 7、图 8：先编号，后并行传输

**图 7（p.665）：创建 request groups。** 主机用每文件短 spin-lock 分配递增 request ID、group ID、组首 request ID，并预留队列位置；释放锁后各线程可以并行发送。基本分组意图是相邻读同组，每个写单独一组。锁只覆盖编号和预留，不覆盖网络与 SSD。

**图 8（p.665）：乱序到达的困难。** R1、W1、W2 可能先到，而排在前面的 R2 仍在网络中。因此“我看到了后一组”不意味着“前组已经完整到达”。单看 group ID 无法安全推进；必须知道前面应完成多少请求。

#### 算法 1（p.666）：通过完成计数确定组间边界

target 为每个队列维护当前组 `curr_gid`、已完成请求总数 `curr_fin_reqs`、各组首 request ID、已接收最大 request ID，以及 request ID 到环位置的映射。

若 request ID 从 0 连续分配，下一组首 request ID 为 k，就意味着前面恰好有 k 个请求。因此满足“下一组是当前组 + 1”且“已完成总数 = k”时，前面所有请求才可视为完成，target 可以推进。

1. Poller 收到当前组请求时立即提交 SSD。
2. 收到下一组且前组已经全完成时，更新当前组并提交。
3. 否则记录请求位置和组首编号，暂缓提交。
4. Finisher 在完成时递增累计计数，达到下一组边界后提交已到达的下一组请求。

**小例子（报告推演）：** G0 有 rid 0、1；G1 的写为 rid 2。如果 rid 2 先于 rid 1 到达，`first_rid(G1)=2`，而只完成 rid 0 时计数为 1，不能执行该写。rid 1 完成使计数达到 2，才能推进 G1。前提包括：每个请求只计完成一次、编号无洞、未来组不能越过当前组执行。

**复杂度分析，非作者定理：** 基本编号和哈希表操作通常均摊 O(1)；待处理状态占 O(N)，N 为队列在途请求数。Finisher 按编号扫描待处理区间，单次推进可能 O(N)，不能因为用了哈希表就称整个算法每次都严格 O(1)。丢失请求、线程在预留后退出、重复通知和队列复用所需机制未展开。

**算法与文字的谨慎核对：** §4 的文字称读请求沿用 group ID、写请求增加 group ID；但若写后紧接读仍沿用同一 ID，就与“每个写独立成组”及图 7 不一致。完整实现需要在写转读时处理组边界。此外算法 1 第 26–29 行先访问 `next_req` 的 group ID、后判断是否为空，初始化、缺失项和扫描端点也未完整说明。因此算法宜作为设计草图，不能不经补充就当作可执行的正确实现；尚无代码证据证明原型实际采用了错误逻辑。

#### 图 9：基本分组与合并分组究竟差在哪里

**图 9（p.666）：RW、Basic Group、Merging Group 时间线。** 基本分组把网络阶段并行化，但独立写仍一组一组提交 SSD。Merging Group 进一步发现不同操作访问互不冲突的区间，可以同组、同时间进入 SSD。

U-Lib 为当前组维护读范围、写范围两棵红黑树：新读检查写树，新写检查读树和写树；有冲突则结束当前组并开始新组，否则加入当前组。读读重叠不构成冲突，读写和写写重叠构成冲突。它合并的是调度组，不是把多个 I/O payload 合成一个大 I/O。

红黑树普通查找插入为 O(log M)，M 是当前组记录数；但要高效回答任意区间重叠，仍需说明区间合并规则或范围索引细节。只凭“按起点排序的红黑树”不能证明所有重叠查询都为 O(log M)。新组建立后清空旧树的开销也应计入。

**机制贡献的区分：** Basic Group 减少被锁串起来的网络等待；Merging Group 利用互不重叠区域的 SSD 并行性。真正重叠的写仍有顺序约束，不能保证线性扩展。图 15(b) 专门检验两者差别。

<a id="atomicity"></a>
### 8.3 失败原子性：日志留在 target，网络只传一次数据

应用用 `atomic_write_start` 开始，普通 `write` 添加更新，`atomic_write_commit` 提交，必要时 `atomic_write_abort` 放弃。常规接口拦截可以减少应用改动，但使用新增事务能力需要显式 API，不能宣称所有应用自动得到多写原子性。

**为什么用 redo：** undo 必须先持久化旧值再覆盖新值，将两段写留在关键路径；redo 先把新值持久化到日志，随后可后台 checkpoint。CetoFS 的收益主要来自将这些步骤放在 target，不是发明了 redo logging。

**图 10（p.667）：事务管理。**

| 结构 | 所在位置 | 用途 |
| --- | --- | --- |
| `mt_table` | DRAM | 活跃事务元数据，记录日志位置与正式数据位置之间的映射 |
| `pt_table` | SSD | 提交后可用于恢复的事务元数据 |
| `t_log` | SSD | 保存新数据日志 |
| `log_index` | DRAM，每请求队列 | 从正式 LBA 找最新日志位置，使未 checkpoint 的数据可被读取 |

运行阶段先把写入数据放进 `t_log` 并更新内存结构；commit 持久化事务元数据到 `pt_table`；后台 checkpoint 复制到正式位置，然后回收日志。图中的 checkpointed、committed、running 三种状态对应不同回收与恢复行为。

**故障语义推演：** 未提交事务应被丢弃；已提交但未 checkpoint 的事务应能从日志重放；checkpoint 完成后才能安全复用相关空间。这要求日志先于提交记录持久化，且提交记录可判断完整性，checkpoint 与日志回收有可靠顺序。原文阐明总体协议，但未给完整恢复算法、torn-write 处理、flush/FUA 细节或系统故障注入结果。

“一次数据跨网”指负载数据不再为 checkpoint 反复经过主机，不是整个事务只有一个网络消息，也不是 SSD 只写一次。start/commit、响应和日志元数据仍有成本；SSD 内部仍需要日志写和正式位置写。作者也承认 `pt_table` 的小写带来放大，提出未来使用 NVMe PMR 优化。

**事务感知提交和完成。** U-Lib 累积事务请求，在事务请求齐备或超过阈值时批量提交；target 批量通知，减少 doorbell/MMIO。代价可能包括等待凑批的延迟和请求缓冲空间。论文未单独给出这项机制的消融或阈值敏感性，不能把原子写全部收益都归给批处理。

**语义边界：** failure atomicity 是崩溃后全有或全无，不能自动推出事务隔离、跨文件事务、跨 target 原子提交或完整 ACID。并发事务和 `log_index` 的可见性、abort 后索引回滚等细节需要进一步核实。

| Delete rand | 2.72 | 2.57 | 2.39 | 2.22 | 18.4% |

计算公式为 `(基线延迟 − CetoFS 延迟) / 基线延迟`。Read hot 使用 1% 热键值对。

**问题与结论：** 每次同步持久化都走下层，所以 Write sync 受益最大；命中 LevelDB block cache 的读不需要远程 SSD，文件系统优化自然被稀释。CetoFS 对 uFS 的 Write sync 延迟下降约 8.6%，而“uFS 比 CetoFS 高多少”用另一分母为约 9.4%；原文“uFS 高 8%”是较粗的表述，不宜当作精确数值。

没有证据表明该实验把 LevelDB WAL 改成使用 CetoFS 显式原子写 API，因此不能把表 3 当作 LevelDB 已利用 §5 事务卸载的应用验证。

<a id="figure-14"></a>
### 9.6 图 14（p.670）：原子写收益与数据搬移位置

**图 14(a)：单线程，改变原子写大小。** 与主机 J-Undo 和 J-Redo 比较；大于 4KB 的原子写拆成多个 4KB 写。原文报告相对 J-Undo 的 “1.8X” 改善以及相对 J-Redo 的平均 58% 提升；鉴于 “outperforms by X” 的表达歧义，前者保留作者倍率写法，不换算为确定百分数。小 I/O 时 CetoFS 明显受益于减少跨网日志控制块写；大 I/O 时这些小块开销被摊薄，与 J-Redo 差距收窄。

**图 14(b)：64KB 原子写，增加线程。** CetoFS 最高，约 12 线程后趋平，作者解释为 SSD 带宽饱和；J-Redo 仍受主机 checkpoint 往返搬运影响，J-Undo 的双重关键路径写更慢。它支持“把日志处理搬到 target”这一收益来源，但并未单独隔离批量 doorbell、日志布局和具体提交实现的贡献。

**不能证明的部分：** 图 14 测的是原子写性能，不是崩溃后的原子性。没有掉电/进程故障注入、恢复时间、未完成 checkpoint 压力和日志空间耗尽实验。长期稳态能否持续清理日志，也不能仅由吞吐曲线判断。

<a id="figure-15"></a>
### 9.7 图 15（p.670）：最有价值的机制归因

**图 15(a)：随机读延迟分解。** 五种状态为 I（无权限检查的理想情况）、A-H（映射及权限全命中）、T-M（映射缺失）、P-M（权限缺失）、A-M（两者均缺失），并与 Ext4 对照。热权限检查额外约 0.2µs；映射缺失比权限缺失更贵，因为前者要从主机经 K-FS 获取映射。全缺失时为 36.7µs，仍低于 Ext4 的 42.34µs，按表中数值计算约下降 13.3%。

它验证了“检查下沉并不必然抵消用户态收益”，但热检查成本不等于所有部署的平均成本；还需知道实际表大小、内存预算和访问分布，不能将 0.2µs 当作固定常数。

**图 15(b)：DWOM 内部变体消融。** RW 在主机长时间持读写锁；BG 让传输并行但 SSD 仍按基本组排序；MG 合并无冲突范围；Ideal 不做锁控制。RW 最差，BG 在低线程数改善但随后停滞，MG 更接近 Ideal。结论是：只去掉网络等待还不够，解除不相交写之间不必要的 SSD 串行化才释放主要扩展性。

Ideal 是性能上界参考，省去正确性约束，不能作为可部署的等价基线。该消融也只在 DWOM 中展示，缺少完全重叠写、读写冲突混合和范围树压力测试。

<a id="section-10"></a>
## 10. 相关工作分析

下表依据原文 §8 的分类和定位；未逐篇独立复核所有被引论文，因此差异应理解为 CetoFS 作者的论述及本报告对其的分析。

| 类别 | 代表工作，括号为原文参考编号 | 与 CetoFS 的联系 | 贡献边界 |
| --- | --- | --- | --- |
| 远程存储栈 | ReFlex [25]、i10 [14]、RIO [33]、Volley [55]、Gimbal [38] | 都降低远程访问成本或管理顺序/QoS | CetoFS 重点是文件系统权限、文件并发和事务；“正交可组合”是设计主张，非已完成集成实验 |
| 用户态与内核协同 | SplitFS [19]、uFS [35]、AugeFS [17] | 用户态减少内核路径；SplitFS 也保留内核功能 | SplitFS 针对 PM，uFS 引入可信服务进程；CetoFS 利用远端可信进程做保护和语义处理 |
| 硬件或设备保护 | Moneta-D [5]、BypassD [54]、Arrakis [46]、DevFS [22]、CrossFS [48] | 都需要允许直接访问同时防止非法块操作 | CetoFS 避免专用 SSD/IOMMU 改造，但仍要求修改 K-FS 并部署 T-Handler |
| 存储服务卸载 | iPipe [36]、LineFS [23]、LeapIO [30]、OS2G [18] | 共同把工作移动到更靠近资源的位置 | CetoFS 当前实测在普通 target CPU；DPU/SmartNIC 迁移属于未来方向 |
| 可扩展文件访问 | CrossFS [48]、Trio [57]、SpanFS [21]、Max [31] | 都处理文件范围、锁或共享元数据争用 | CetoFS 强调网络参与的锁等待；请求分组并非首次发现范围冲突可并行 |

**真正的差异不在单个名词：** redo、范围冲突检测、用户态 I/O 和权限表都各有先例。本文的组合洞察是，用主机内核建立授权和元数据，用用户态缩短数据路径，用可信存储端承接必须集中决定的语义，让这些决定尽量不再引入额外主机往返。

<a id="section-11"></a>
## 11. 讨论、贡献与研究启发

### 11.1 作者明确承认的成本与未来方向

§7 测得文件打开额外约 5µs，占 open 总时间约 31%。长生命周期文件可摊薄，短命小文件则未必。把这一开销称为“一次性”没有消除频繁 open/close 工作负载的代价。

多 SSD/多 target 可考虑组成逻辑设备，多 initiator 则需要 OCFS2 式分布式锁扩展；这些都留作未来工作。DPU/SmartNIC 移植及借助加速器压缩、加密同样没有已报告的实测结果。不能将本文描述成已解决多节点文件系统一致性或已部署 DPU 文件系统。

### 11.2 技术贡献及其必要性

1. **测量驱动的问题定位。** 分离远程物理设备延迟和内核处理代价，说明仅减少 syscall 或仅升级网络不足以解决问题。
2. **控制面复用、数据面旁路以及 target 授权检查。** 回应用户态直接访问与文件保护间的冲突。
3. **主机编号、target 排序以及无冲突组合并。** 同时减少网络阶段串行化和不必要的设备阶段串行化。
4. **target redo 及事务感知批处理。** 将 checkpoint 数据路径留在存储端，并摊薄 doorbell 开销。

### 11.3 对 Mooncake／远程存储实验的可迁移启发

以下是研究建议，**不是对当前 Mooncake 代码实现的审计结论，也不是已完成的改造**。

最值得借鉴的是按“语义要求发生在哪里”拆开端到端路径：先确认瓶颈是传输、目标端排队、锁覆盖网络、数据拷贝还是持久化提交，再决定卸载位置。对象/KV 系统未必需要 inode 权限表，但仍可能需要可信端校验对象归属、版本、访问能力及其撤销；文件内 range group 的设计也不能直接等同于 KV 对象事务。

如果要基于本文设计一组最小但有说服力的实验，可以按以下顺序推进：

1. 固定硬件与持久化语义，对比裸远程 I/O、内核文件路径、用户态路径，拆出网络、软件和 SSD 时间。
2. 固定 CPU 核预算，对比主机持锁、只移动排序、再增加非冲突并行，分别测私有对象、共享对象不同范围和真正重叠更新。
3. 对比主机与 target checkpoint，记录每事务跨网字节、SSD 写字节、提交延迟和后台积压，而不仅是最终吞吐。
4. 补充冷权限/映射、频繁打开、长尾延迟、日志耗尽和故障恢复，让性能主张与正确性主张使用各自合适的证据。

对于已有 RDMA 或 NVMe-oF 快路径的系统，最有价值的新增机制未必是再次“用户态化”，而可能是缩短跨网络的串行区间和避免持久化数据回流。这个判断仍应由实际测量决定。

## 12. 审稿人视角总结

<a id="review"></a>
### 12.1 优点、不足与关键问题

**优点。** 三个动机与三项设计对应清楚；权限保护作为用户态化的必要前提被显式处理；图 15 将“网络并行”和“设备并行”区分开，是有解释力的内部消融。测试既有微基准，也有 Filebench 和 LevelDB；Varmail、热块读及缓存读结果使适用边界可见。

**不足按影响排列：**

| 问题 | 为什么影响结论 | 需要补充的证据 |
| --- | --- | --- |
| 崩溃原子性和权限并发更新缺少验证 | 二者是设计正确性的核心，吞吐不能代替证明 | commit/checkpoint/回收故障注入；权限撤销与块复用竞态测试 |
| 工作负载、语义与资源预算公平性未完全展开 | uFS worker 数、远程改造及不同持久化模式可能影响对比 | 确定版本、配置、CPU 绑定、相同核预算和相同持久化保证 |
| 单 initiator、单 target、单 SSD | 无法证明多节点一致性、容错和容量规模下的表现 | 多设备/多主机实验及对应协议 |
| 并发算法文字和伪代码存在省略或不一致 | 读写组边界、空洞扫描影响可复现性和正确性审查 | 完整实现、顺序不变量及异常路径说明 |
| 缺少 tail latency、CPU、误差及稳态日志数据 | 轮询/批处理可能以资源和尾延迟换吞吐 | 重复运行、置信区间、p99、每核吞吐、长期 checkpoint 压力 |
| 平台较窄 | Linux 5.5、单 Optane 和特定 RDMA 实现未覆盖更多系统 | 当前内核、不同 SSD 以及有代表性的传输/用户态基线 |

**关键问题逐一回答：**

- 为什么会有这种方法？表 1–2 和图 2–4 较充分地说明了在所测系统中，软件栈、跨网持锁和主机日志搬运会成为瓶颈。
- 它怎么解决问题？可信 target 授权支持用户态快路径；主机短锁只编号、target 按组执行缩短了网络串行区间；日志卸载把 checkpoint 留在数据端。机制链条合理。
- 实验充分验证了吗？性能方面支持主要方向，图 15 的归因较强；安全性、崩溃恢复、资源效率和规模化方面仍缺证据。
- 与相关工作的区别显著吗？贡献主要在远程文件系统场景下的跨层职责组合，不能把已有的 redo、红黑树或用户态 bypass 单独算成全新原理。
- 最高改善能推广吗？不能。最大收益与共享文件非冲突写、基线的串行化及当前平台有关；真实冲突、元数据密集或应用缓存命中的场景收益较小。

**结论置信度：** 对架构分工、表中数据、实验类型和已承认的扩展边界为高；对最大 19× 的具体取点、未公开实现中的算法细节和真实故障正确性保持未确认。没有代码和独立复现，不给出 Accept/Reject 或数值评分。
