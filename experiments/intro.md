# 题目

- Transparent Heterogeneous Storage for KV Cache across Local and Remote NVMe
- （解耦idea优先）Decoupling KV Cache Management from Storage Topology with Transparent Heterogeneous Storage
- （技术点优先）Unified Object Lifecycle Management for Heterogeneous KV Cache Storage
## 1 引言

（KV Cache 的容量和资源调度问题）大语言模型（Large Language Model，LLM）的上下文长度与并发请求规模持续增长，使键值缓存（Key-Value Cache，KV Cache）逐渐成为推理系统的主要容量开销之一。KV Cache 保存已处理上下文的中间状态，可避免在请求恢复或后续解码时重复计算，但其容量随上下文长度、批量大小和并发度增加。当 GPU 显存无法容纳全部缓存时，系统需要将暂时不活跃或被抢占请求的 KV Cache 卸载到 CPU 内存或外部存储，并在请求恢复时重新读取。外部存储因而不仅承担容量扩展，还直接影响缓存写入、恢复和回收的端到端开销。

（local/remote storage 的 tradeoff 与机会）作为常用的外部存储，本地 NVMe SSD 能够以低于内存的单位容量成本提供持久化空间，但其容量和 I/O 带宽受单节点硬件限制，并可能与同节点的其他 I/O 任务竞争。NVMe over Fabrics（NVMe-oF）允许推理节点通过高速网络访问远端 NVMe SSD，将分散设备组织为共享存储资源。本地 NVMe 无需网络传输，通常更适合延迟敏感的访问；NVMe-oF 增加了网络与协议开销，却能够在本地容量不足或 I/O 竞争加剧时提供独立的容量和带宽。**因此，系统需要根据访问需求和资源状态，在本地 NVMe 与远端 NVMe-oF 存储之间进行协调与选择，以利用两类资源的互补性。**

（后端感知的 placement 与生命周期管理） 当 KV Cache 系统同时使用本地与远端存储时，不同存储后端及其拓扑差异仍可能向上层暴露，使缓存管理逻辑与具体存储部署形态产生耦合。当部署形态从单节点本地 SSD 扩展到远端 SSD 池，或对象的 placement 策略发生变化时，上层管理逻辑也需要随之调整。这种后端依赖增加了系统实现和运维复杂度，并限制了本地与远端资源之间的透明调度与扩展。因此，现有设计中的本地与远端存储资源仍以相互区分的后端形式存在，其容量与性能互补性难以被抽象为对上层 KV Cache 管理逻辑透明的统一存储资源池。

（本文提出透明异构存储层）基于这一观察，本文探索一种**面向 KV Cache 的透明异构存储设计**：在保持统一对象接口的同时，将本地 NVMe 与 NVMe-oF 的选择收敛为存储系统内部的资源管理决策，并保证不同后端上的对象具有一致、可恢复的生命周期语义。这里的透明性主要指**存储后端透明**：上层 KV Cache 管理逻辑仍负责决定对象何时创建、淘汰、恢复或复用，但无需感知对象最终被放置在本地 NVMe 还是远端 NVMe-oF。该设计使上层 KV Cache 管理逻辑与异构存储后端的放置和拓扑解耦，在不改变对象访问方式的情况下利用更大的容量空间和可组合的 I/O 资源，并将后端选择、放置、故障处理和后端扩展限制在存储系统内部。

要实现这样的透明统一存储抽象，需要解决两个关键问题。
- （Challenge 1：Placement transparency）首先，**本地 NVMe 与 NVMe-oF 在资源分配、数据传输、对象寻址和访问路径上存在差异**。如果这些差异暴露给上层组件，KV Cache 管理逻辑就需要感知具体存储拓扑，并分别维护与不同后端对应的放置和访问路径。因此，透明层需要在不改变对象访问接口的前提下，将后端选择、对象放置和读取路由封装在 Store 内部，使对象能够以统一方式被创建和访问，而无需由上层显式指定具体后端。
- （Challenge 2：Lifecycle consistency）其次，统一接口并不意味着不同后端天然具有一致的对象语义。本地 NVMe 与 NVMe-oF 在资源分配、写入完成和地址管理方式上存在差异，简单地在不同路径之间进行条件分发无法保证对象具有一致的可见性和恢复语义。写入失败时不能发布不完整对象，客户端重启后也不能依赖进程内映射恢复对象位置。因此，后端选择必须与元数据提交、失败撤销、读取路由和资源释放保持一致，并能够从持久化的副本描述恢复对象。

（实现透明后端解耦与统一生命周期）为解决上述挑战，本文在 Mooncake Store 中设计并实现透明异构存储层。
- 针对后端解耦，上层继续通过统一的 `put`、`get` 和 `remove` 接口管理 KV Cache，无需指定对象写入本地 NVMe 还是远端 NVMe-oF；Master 通过 `local_only`、`remote_only` 和 `round_robin` 三种策略选择写入目标，并以已提交的副本元数据作为读取和删除的路由依据。
- 针对生命周期可靠性，本地与远端路径均遵循“准备—写入—提交/撤销—读取—删除”的对象语义：数据完成写入后才发布为可读副本，失败操作撤销待提交元数据并释放对应资源，客户端重启后则从 Master 返回的副本描述恢复访问路由。该设计将异构后端的放置决策和实现差异限制在 Store 内部，使上层 KV Cache 管理逻辑无需随部署拓扑或后端选择变化。

我们在两节点测试床上通过配对微基准、生命周期故障测试、KV Cache 工作负载和 FAST’25 公开轨迹评估该设计。配对结果显示，透明层对本地 NVMe 的影响很小；在 16–256 KiB 对象上，`put` 的 p50 增量为 −0.00%–5.79%。远端路径的额外开销主要出现在写入，`put` p50 增量为 13.99%–19.78%。考虑到基线延迟处于亚毫秒量级，我们同时报告绝对延迟：以 128 KiB 对象为例，延迟从 0.2432 ms 增至 0.2814 ms，即增加 0.0382 ms；`get` 和 `remove` 的 p50 绝对增量则分别为 0.0001 ms 和 0.0003 ms。我们进一步在 `local_only`、`remote_only`、`round_robin`、目标不可用和客户端重启场景中验证了对象生命周期：失败写入不会发布不完整对象，已分配资源能够回收，客户端重启后仍可依据 Master 元数据恢复访问。在 FAST’25 `conversation` 和 `toolagent` 轨迹的顺序 Store 回放中，透明路径带来的请求 p50 增量分别为 2.47%–8.42%（本地）和 11.95%–12.08%（远端），说明在包含缓存复用和淘汰的请求序列中，单次写入的额外开销会被部分摊薄。由于轨迹回放不包含并发 serving 和 GPU 执行，我们将其用于刻画透明存储路径在请求序列中的开销，而不将结果外推为端到端 LLM serving 性能结论。总体而言，上述结果表明，该透明层以较小且可度量的代价换取了后端解耦和统一的生命周期管理。

本文的主要贡献如下：
1. **透明异构存储抽象。** 提出面向 KV Cache 的透明异构存储抽象，在统一对象接口下封装本地 NVMe 与 NVMe-oF，将上层 KV Cache 管理逻辑与具体存储后端的放置和拓扑解耦，使上层无需感知对象最终所在的存储后端。
2. **统一且可恢复的对象生命周期。** 设计跨本地 NVMe 与 NVMe-oF 的统一对象生命周期机制，将后端选择与元数据提交、失败撤销、读取路由和资源释放关联起来，保证对象具有一致的可见性和可恢复语义，并支持客户端重启后的访问路由恢复。
3. **分层评估与工作负载边界分析。** 通过同后端配对实验量化透明层自身开销，通过故障与重启场景验证对象生命周期的正确性，并结合 KV Cache 工作负载与 FAST’25 `conversation`、`toolagent` 轨迹回放，刻画透明存储路径在不同访问模式下的开销及其适用边界。
