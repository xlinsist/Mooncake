# 题目

- Transparent Heterogeneous Storage for KV Cache across Local and Remote NVMe
- （解耦idea优先）Decoupling KV Cache Management from Storage Topology with Transparent Heterogeneous Storage
- （技术点优先）Unified Object Lifecycle Management for Heterogeneous KV Cache Storage
## 1 引言

（KV Cache 的容量和资源调度问题）大语言模型（Large Language Model，LLM）的上下文长度与并发请求规模持续增长，使键值缓存（Key-Value Cache，KV Cache）逐渐成为推理系统的主要容量开销之一。KV Cache 保存已处理上下文的中间状态，可避免在请求恢复或后续解码时重复计算，但其容量随上下文长度、批量大小和并发度增加。当 GPU 显存无法容纳全部缓存时，系统需要将暂时不活跃或被抢占请求的 KV Cache 卸载到 CPU 内存或外部存储，并在请求恢复时重新读取。外部存储因而不仅承担容量扩展，还直接影响缓存写入、恢复和回收的端到端开销。

（local/remote storage 的 tradeoff 与机会）作为常用的外部存储，本地 NVMe SSD 能够以低于内存的单位容量成本提供持久化空间，但其容量和 I/O 带宽受单节点硬件限制，并可能与同节点的其他 I/O 任务竞争。NVMe over Fabrics（NVMe-oF）允许推理节点通过高速网络访问远端 NVMe SSD，将分散设备组织为共享存储资源。在相同设备和可比 I/O 路径下，本地访问不经过网络，能够避免 NVMe-oF 的网络与协议开销；远端 NVMe-oF 则能够提供独立于推理节点的容量和 I/O 资源。**因此，部署者需要能够按照容量规划和既定部署策略选择本地或远端存储，同时避免这种选择渗透到上层 KV Cache 管理逻辑中。**

（后端感知的 placement 与生命周期管理）以 Mooncake Store 为例，调用方需要通过 `ReplicateConfig` 显式设置本地副本数、NoF 副本数或目标 segment，从而将后端选择和部分拓扑信息暴露给上层。当部署形态从单节点本地 SSD 扩展到远端 SSD 池，或部署者改变对象 placement 策略时，调用方也需要调整配置与访问逻辑。这种后端依赖增加了系统实现和运维复杂度，也使本地与远端资源难以在不修改上层代码的情况下作为统一存储资源使用。因此，本文关注的问题不是如何动态求解最优 placement，而是如何将**由部署配置控制的后端选择**收敛到 Store 内部，并为两类后端提供一致的对象接口与生命周期语义。

（本文提出透明异构存储层）基于这一观察，本文探索一种**面向 KV Cache 的透明异构存储设计**：在保持统一对象接口的同时，将本地 NVMe 与 NVMe-oF 的选择收敛为由部署配置控制的 Store 内部决策，并保证不同后端上的对象具有一致、可恢复的生命周期语义。这里的透明性主要指**存储后端透明**：上层 KV Cache 管理逻辑仍负责决定对象何时创建、淘汰、恢复或复用，但无需感知对象最终被放置在本地 NVMe 还是远端 NVMe-oF。该设计使上层 KV Cache 管理逻辑与异构存储后端的放置和拓扑解耦，在不改变对象访问方式的情况下接入本地与远端容量，并将后端选择、对象放置和访问路由限制在 Store 内部。

要实现这样的透明统一存储抽象，需要解决两个关键问题。
- （Challenge 1：Placement transparency）首先，**本地 NVMe 与 NVMe-oF 在资源分配、数据传输、对象寻址和访问路径上存在差异**。如果这些差异暴露给上层组件，KV Cache 管理逻辑就需要感知具体存储拓扑，并分别维护与不同后端对应的放置和访问路径。因此，透明层需要在不改变对象访问接口的前提下，将后端选择、对象放置和读取路由封装在 Store 内部，使对象能够以统一方式被创建和访问，而无需由上层显式指定具体后端。
- （Challenge 2：Lifecycle consistency）其次，统一接口并不意味着不同后端天然具有一致的对象语义。本地 NVMe 与 NVMe-oF 在资源分配、写入完成和地址管理方式上存在差异，简单地在不同路径之间进行条件分发无法保证对象具有一致的可见性和恢复语义。写入失败时不能发布不完整对象；客户端进程重启后，也不能依赖旧进程中的映射恢复对象位置。因此，后端选择必须与元数据提交、失败撤销、读取路由和资源释放保持一致，并能够在 Master 元数据仍可用时从副本描述恢复访问路由。

（实现透明后端解耦与统一生命周期）为解决上述挑战，本文在 Mooncake Store 中设计并实现透明异构存储层。
- 针对后端解耦，上层继续通过统一的 `put`、`get` 和 `remove` 接口管理 KV Cache，无需指定对象写入本地 NVMe 还是远端 NVMe-oF；部署者在 Master 端配置 `local_only`、`remote_only` 或 `round_robin` 策略，Master 据此选择写入目标，并以已提交的副本元数据作为读取和删除的路由依据。
- 针对生命周期可靠性，本地与远端路径均遵循“准备—写入—提交/撤销—读取—删除”的对象语义：数据完成写入后才发布为可读副本，失败操作撤销待提交元数据并释放对应资源，客户端重启后则从 Master 返回的副本描述恢复访问路由。该设计将异构后端的放置决策和实现差异限制在 Store 内部，使上层 KV Cache 管理逻辑无需随部署拓扑或后端选择变化。

我们在两节点测试床上通过同后端配对微基准、生命周期测试、受控 KV Cache 工作负载和 FAST’25 公开轨迹评估该设计。配对结果显示，在 16–256 KiB 对象上，本地 NVMe `put` 的 p50 增量为 −0.00%–5.79%，且不同大小下没有一致的退化方向；远端 NVMe-oF `put` 的 p50 增量为 13.99%–19.78%，额外成本主要集中在写入。以 128 KiB 对象为例，远端 `put` 延迟从 0.2432 ms 增至 0.2814 ms，即增加 0.0382 ms；`get` 和 `remove` 的 p50 绝对增量分别为 0.0001 ms 和 0.0003 ms。我们进一步在 `local_only`、`remote_only`、`round_robin`、目标不可用和客户端重启场景中验证对象生命周期：失败写入不会发布不完整对象，已分配资源能够回收，新客户端能够依据 Master 返回的副本描述恢复访问路由。受控 reuse sweep 显示，当 reuse 从 0% 提高到 90% 时，远端请求 p50 的透明层增量从 15.31% 降至 0.01%，而请求 p95 仍有 13.93% 增量；该结果表明，高复用请求序列能够降低写入成本对中位请求延迟的影响，但不会消除包含写入请求的尾部开销。在 FAST’25 `conversation` 和 `toolagent` 的 1000-request、arrival-paced 顺序 Store 回放中，远端透明路径的总存储等待增量分别为 11.97% 和 13.71%。这些回放不包含并发 Store 调用、GPU 执行或完整 LLM serving，因此仅用于刻画透明存储路径在请求序列中的开销。总体而言，上述结果表明，该透明层以较小且可度量的代价换取了由部署配置控制的后端解耦和统一对象生命周期。

（内部备注：Master 路径短时中断实验仍观察到 failed-put lifecycle residue；投稿前应修复该问题，或将“资源能够回收”的结论限定为当前已覆盖的目标不可用与写入失败场景。）

本文的主要贡献如下：
1. **透明异构存储抽象。** 提出面向 KV Cache 的透明异构存储抽象，在统一对象接口下封装本地 NVMe 与 NVMe-oF，将上层 KV Cache 管理逻辑与具体存储后端的放置和拓扑解耦，使上层无需感知对象最终所在的存储后端。
2. **统一且可恢复的对象生命周期。** 设计跨本地 NVMe 与 NVMe-oF 的统一对象生命周期机制，将后端选择与元数据提交、失败撤销、读取路由和资源释放关联起来，保证对象具有一致的可见性和可恢复语义，并支持客户端重启后的访问路由恢复。
3. **分层评估与工作负载边界分析。** 通过同后端配对实验量化透明层自身开销，通过故障与重启场景验证对象生命周期的正确性，并结合 KV Cache 工作负载与 FAST’25 `conversation`、`toolagent` 轨迹回放，刻画透明存储路径在不同访问模式下的开销及其适用边界。
